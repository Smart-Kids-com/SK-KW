# المخزون عند حفظ الطلب

يُجمع المنتج المكرر قبل التسعير والتحقق من المخزون. حفظ الطلب وعناصره واستخدام كود الخصم والحجز عملية كتابة واحدة في قاعدة البيانات. شروط الحجز تفحص on_hand - committed - unavailable فعلياً داخل المعاملة؛ الفحص السابق للمعاملة للإبلاغ المبكر فقط. لا توجد أقفال أو حجوزات في ذاكرة الخادم. فشل أي منتج يلغي كل الحجوزات والطلب والعناصر واستخدام الخصم.

سجل order_inventory مستقل عن الملاحظات، وله انتقالات محددة: reserved → fulfilled أو released؛ ثم fulfilled → restocked. تكرار العملية لا يغير المخزون ثانية. الحجز يزيد committed ويقلل stock؛ التنفيذ يقلل on_hand وcommitted؛ الإلغاء يحرر الحجز فقط؛ إعادة التخزين تعيد الكمية المنفذة أو تحرر الحجز غير المنفذ. إلغاء طلب منفذ لا يعيد بضاعة مشحونة تلقائياً؛ يلزم إجراء restock الصريح. تسجيل return وحده يبقى علامة إدارية ولا يفترض عودة البضاعة.

محفزات قاعدة البيانات تربط المسارات الفردية والجماعية وPUT العام بالحجز، فلا تتجاوزها طرق تغيير الحالة البديلة. shipped وcompleted يمثلان التنفيذ وفق حالات النظام الحالية؛ mark-paid الحالي يضع completed وبالتالي يطبق نفس الأثر، مرة واحدة. archive لا يحرر الحجز، وunarchive يحافظ عليه؛ الحذف يحرر الحجز غير المنفذ دون إعادة بضاعة منفذة. تعديل عناصر طلب غير منفذ يعيد توزيع الحجز داخل معاملة واحدة، والفشل يعيد العناصر والكميات السابقة. تعديل عناصر منفذة/إعادة إحياء طلب محرر أو مسترجع مرفوض. نسخ الطلب ينشئ طلباً pending جديداً بأسعار قاعدة البيانات، يخضع للحجز والخصم الحاليين ولا ينسخ حجزاً قديماً.

صفحة checkout تحفظ checkoutKey عبر المحاولات وإعادة تحميل الصفحة. إعادة المفتاح والطلب نفسه تعيد الطلب المحفوظ دون حجز أو خصم أو إرسال إضافي. تغيير بيانات الطلب مع المفتاح نفسه يُرفض. الحذف يحتفظ بعلامة للمفتاح تمنع إعادة إنشاء الطلب عن طريق إعادة المحاولة. العملاء البرمجيون يجب أن يرسلوا Idempotency-Key أو checkoutKey ثابتاً لكل محاولة شراء؛ بدون مفتاح لا يمكن تمييز إعادة المحاولة عن شراء جديد مقصود.

## قبل النشر

دالة migrateOrderInventory في db/order-inventory-migration.js تجهز أعمدة إدارة المخزون ومفتاح المحاولة، سجل الحجز والمحاولات المحذوفة، الفهرس والمحَفّزات. لا يستدعيها server.js ولا مسارات الطلبات. تستخدمها البيانات الوهمية والاختبارات فقط. يلزم قبل النشر فحص مخطط القاعدة المستهدفة وتطبيق ترحيل الأسعار والمخزون بتفويض منفصل، والتأكد من وجود أعمدة المنتجات المستخدمة في المخزون.

الطلبات القديمة تبقى inventory_managed=0؛ لا ننشئ حجوزات لها أو نعدل رصيداً بناء على تخمين. يلزم تسوية الطلبات القديمة المفتوحة مع on_hand وcommitted قبل التفعيل حتى لا تُحسب كميات متاحة وهي مرتبطة بطلبات قديمة. راجع كذلك مطابقة completed/mark-paid مع سير عمل التشغيل الفعلي؛ فصل الدفع عن التنفيذ يحتاج تعريفاً مستقلاً لحالة الدفع ولم تُغيّر دلالته الحالية هنا.

## التحقق

`npm run test:checkout` يشغل اختبارات الطلب والمخزون وشراءً كاملاً في Chrome/Edge محلي نظيف على التطبيق الحقيقي. قاعدتا المتجر والمصادقة ملفان مؤقتان. تُمنع إعدادات التشغيل وdotenv والشبكة الخارجية والبريد وMeta، وتُستبدل مكتبة Pixel في غلاف الاختبار فقط. يقرأ الاختبار الطلب والعناصر والحجز ورصيد المنتج من قاعدة الاختبار مباشرة.

يشمل التحقق التزامن عبر HTTP وعبر اتصالين مستقلين، جمع المكرر، إعادة مفتاح الشراء، الإلغاء والتنفيذ والاسترجاع المتكرر، تحديث الحالة وتعديل العناصر والحذف، فشل الحفظ لمنتج لاحق مع التراجع الكامل، والمخطط القديم والجديد. أُنجزت رحلة المنتج → السلة → الخصم والشحن → إكمال الطلب → صفحة الشكر، مع حفظ 10 د.ك منتجات، 1 خصم، 2 شحن، 11 إجمالي، وحجز وحدتين. لم يُختبر Turso خارجي أو تعدد مناطق Vercel أو مدفوعات وبريد/Meta حقيقية؛ لا نشر أو تغيير لبيانات التشغيل.
